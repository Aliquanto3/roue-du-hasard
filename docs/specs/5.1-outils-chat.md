# Story 5.1 — Outils et contrat du chat (V1.1)

Cadrage : `docs/v1.1-chat-slm.md`. Corpus : `docs/v1.1/`. Tout le code est dans `src/chat/`, jamais importé par `src/main.ts`.

## Critères d'acceptation
- C1. `types.ts` : `Decision` (forme de `attendu` du corpus, plus `confirmation`), `EtatChat`, `Etage` (`decider(commande, etat, signal)` rend un `ResultatEtage` ou `null`), `ResultatEtage` (décision, confiance, données de trace), `TraceEtage` (étage, entrée, sortie brute, durée).
- C2. `cascade.ts` : étages essayés dans l'ordre, arrêt au premier résultat, traces de tous les étages essayés ; un étage s'enregistre par une ligne de `ETAGES_ENREGISTRES` ; sans résultat, refus `incompris` ; une exception d'étage passe la main (tracée) ; un signal annulé arrête (refus `annule`).
- C3. `outils.ts` : 17 outils, un par action cible du corpus, avec description française et schéma JSON (`definitionsOllama`), validation, correspondance vers `actions.ts`, résolution nom vers id, confirmation calculée (`effacerHistorique`, `reinitialiserCouleurs`, au moins 2 suppressions). Exécution par `Actions.executer` seulement.
- C4. Résolution : sans accents ni casse ; homonyme sans précision donne `clarifier` (sauf une étape par homonyme, « supprime les deux Marie ») ; nom absent proche d'un nom de la liste (inclusion ou 1 faute, 2 au-delà de 5 lettres) donne `clarifier`, sinon `refuser` `nom-absent` (comme le corpus, `abs-01` etc.) ; un nom hostile reste une donnée.
- C5. Écarts du corpus réglés côté outils : `retirerGagnants` vers `definirRetirerGagnants({valeur: actif})`, `renommer.nouveau` vers `nom`, `modeProjection` refusé `indisponible` (story 7.1). `actions.ts` gagne `afficherCadeauSuivant` (lecture seule, sans verrou de rotation, rend `Resultat.cadeauSuivant`).

- C6. Plans sûrs : deux étapes sur la même personne dont une la supprime ou la renomme donnent `refuser` `conflit-etapes` ; des homonymes ne passent que pour « supprime les deux » (autant de `supprimer` que d'homonymes), sinon `clarifier` ; `executerPlan` est tout ou rien (essai à blanc par `Actions.essayer`, copie de l'état, puis application) ; la forme de toute décision est vérifiée (`formeValide`, sinon `refuser` `forme-invalide`).
- C7. Cascade : une décision rendue après `abort()` est ignorée (refus `annule`) ; `ETAGES_ENREGISTRES` est une liste de fabriques `(OptionsEtages) => Etage` (client, URL, modèle pour la 5.6), toujours une ligne par étage.
- C8. Contrat étendu (5.6) : `creerCascade(options)` construit les étages une fois (instance durable du panneau 5.5) et rend `{ etages, decider }` ; `decider` seul reste sans état (tests, banc). Un étage rend un `ResultatEtage`, `null` ou un `PasseMain { decision: null, raison, trace }` ; `TraceEtage.raison?` garde le code court (`indisponible`, `delai`, `json-invalide`, `sans-outil`, `outil-inconnu`, `parametres-invalides`, …). `EtatChat` gagne `prochainCadeau?` (`cadeaux[attribues]`, calculé par l'application) et `historique?` ; `OptionsEtages` gagne `think`, `temperature`, `delaiMs`. `validerParametres` ne lit que les clés propres (`Object.hasOwn`).
- Note : Ollama ignore `pattern` et `additionalProperties` des schémas ; la validation locale suffit.

## Vérification
`src/chat/outils.test.ts` lit le corpus (222 lignes) : outils = actions cibles, plan et confirmation de chaque ligne conformes à `attendu`. `cascade.test.ts`, `actions.test.ts` (nouvelle action, verrou).

## Reports
- Aucun étage branché (5.3, 5.6, 5.10) ; pas d'interface de chat ni de fenêtre d'inspection.
- La demande de confirmation à l'utilisateur est à la charge de l'appelant (`plan.confirmation`).
